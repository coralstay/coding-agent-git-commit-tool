# 1.01 배경과 문제

coding-agent-git-commit-tool은 Sigkill Foundry의 계측 컴포넌트다(최상위 3.03 §3) — 코딩 에이전트가 만드는 git 커밋을 검사하고, 그 커밋을 누가 · 어떤 도구와 모델로 · 무슨 태스크로 · 얼마를 들여 만들었는지 커밋 안에 트레일러로 남긴다.

## 무엇을 하는가

커밋할 때마다 두 가지를 한다.

1. **검사** — 사람(또는 에이전트)이 쓴 제목 · 본문이 정해진 형식을 따르는지, 브랜치명에 태스크 번호가
   있는지 확인하고, 어기면 커밋을 거부한다.
2. **기록** — 통과한 커밋 끝에 `Task-Id` · `AI-Tool` · `AI-Model` · `Tokens-Used` · `Tool-Calls` ·
   `Hooks-Commit` 같은 트레일러를 자동으로 붙인다. 사람이 타이핑하지 않는다.

```text
[docs][backlog] DRAFT-18을 GF-136으로 승격          ← 사람(또는 에이전트)이 쓴다

왜 바꿨는지 설명하는 본문. 한 줄 72자 이내.            ← 선택

Task-Id: GF-136                                     ↓ 아래는 전부 훅이 붙인다
AI-Tool: claude-code
AI-Tool-Version: 2.1.267
Co-Authored-By: Claude <noreply@anthropic.com>
AI-Model: claude-opus-5
Tokens-Used: in=5067994 out=15794
Tool-Calls: 31
Hooks-Commit: c828491
Signed-off-by: cpu-once <231006716+cpu-once@users.noreply.github.com>
```

목표는 `git log` 한 번으로 "무엇을, 왜, 누가(사람인지 어떤 모델인지), 얼마를 써서 바꿨는지"가 읽히는
것이다. 동작은 `core.hooksPath` · `init.templateDir` · `git interpret-trailers` 같은 git 자체 기능과
Python 3 표준 라이브러리만으로 이뤄진다.

## 문제

에이전트가 커밋을 대량으로 남기면 이력이 작업 로그 구실을 해야 한다. 그런데 git의 기본 커밋에는 그
구실에 필요한 정보가 없고, 있는 정보도 믿을 수 없게 되기 쉽다.

| 문제 | 왜 생기는가 | 이 컴포넌트의 대응 |
| --- | --- | --- |
| 커밋이 어느 작업의 일부인지 모른다 | 태스크 번호를 커밋마다 손으로 쓰게 하면 잊고, 강제할 방법이 없다 | 작업을 시작할 때 한 번 정하는 브랜치명에서 태스크 번호를 읽어 강제하고 `Task-Id`로 남긴다(decision-4) |
| 사람 커밋과 에이전트 커밋이 구별되지 않는다 | 커밋 객체에는 author · committer만 있고 도구 · 모델이 없다 | `AI-Tool` · `AI-Tool-Version` · `AI-Model`을 남긴다(decision-5) |
| 에이전트가 말한 값은 믿을 수 없다 | 모델명 · 토큰 수를 에이전트에게 물으면 자가신고가 된다. 토큰 수는 모델이 아는 값이 아니라 API가 응답마다 실어 주는 메타데이터다 | 값은 Claude Code가 하위 프로세스에 주입하는 환경변수와, API 응답을 그대로 기록한 세션 트랜스크립트(`message.model` · `message.usage`)에서만 얻는다(decision-5 · decision-20) |
| 작업의 비용이 이력에 남지 않는다 | 토큰 사용량은 세션 단위로만 보이고 커밋과 이어지지 않는다 | 이 커밋이 바꾼 파일을 실제로 건드린 응답의 토큰을 합해 `Tokens-Used: in=<입력> out=<출력>`으로 남긴다(decision-27) |
| 검사를 건너뛸 수 있다 | `git commit --no-verify`는 `commit-msg`를 건너뛴다 | 건너뛸 수 없는 `prepare-commit-msg`로 강제를 옮기고, 건너뛴 사실은 `Verify-Bypassed`로 기록한다(decision-3 · decision-18) |
| 기록이 나중에 거짓이 된다 | rebase · force push로 커밋을 다시 만들면 트레일러가 자기 커밋에 대해 거짓을 말한다 — 실측에서 `Signed-off-by`와 실제 커미터가 어긋났다 | 이력은 append-only로 둔다. push된 이력의 보호는 원격 저장소 설정이 맡는다(decision-24) |
| 훅에 버그가 있으면 어느 커밋이 영향을 받았는지 모른다 | 훅 버전이 커밋에 남지 않는다 | 이 커밋을 검사한 훅 클론의 커밋 해시를 `Hooks-Commit`으로 남긴다(decision-5) |

## 다루는 범위 — 세 기둥

git 이력을 작업 로그로 만드는 데 필요한 세 가지다(decision-25). 세 기둥은 서로를 필요로 한다 —
이력이 다시 쓰이면 트레일러가 거짓이 되고, 기록할 내용이 정형화돼 있지 않으면 지킬 가치가 줄어든다.

| 기둥 | 하는 일 | 해당하는 것 |
| --- | --- | --- |
| 형식 | 사람이 쓰는 제목 · 본문을 정해진 양식으로 | 제목 · 본문 검증, 에디터 경로 거부, 커밋 단위 규칙(decision-22) |
| 출처 기록 | 누가 · 어떤 도구와 모델로 · 얼마를 들여 만들었는지 자동으로 남김 | 트레일러 전체, 토큰 측정, `AI-Model` 게이트, `Task-Id` 브랜치 강제 |
| 이력 불변 | 한 번 남긴 기록은 다시 쓰지 않음 | append-only 정책(decision-24), 원격 저장소 설정(doc-20) |

용어로 말하면 trail(감사 추적)이 세 기둥 전체이고, provenance(출처 기록)가 두 번째 기둥이다.
attestation(서명된 증명)과 audit(사후 검사)이 어느 훅 · 함수 · 설정에 구현돼 있는지는 doc-21 개념
지도에 있다.

**다루지 않는 것.** 언어별 lint는 세 기둥 어디에도 속하지 않고 사용자에게 언어 도구를 전제하게 만들어
범위에서 뺐다(decision-23). push 단계에서 테스트 · 빌드를 돌리지 않는다(decision-12).

## Sigkill Foundry 안의 자리

| 항목 | 내용 |
| --- | --- |
| 층 | 계측 — 커밋 형식 검사 · 트레일러(태스크 · 모델 · 토큰) 부착 (최상위 3.01 컴포넌트 지도) |
| 어디서 도는가 | 대상 저장소의 git 훅(`core.hooksPath`). 에이전트 프로세스의 커밋이 이 훅을 거친다 |
| 구현하는 최상위 요구사항 | TRL-001 ~ TRL-009, NFR-004 · NFR-005 (최상위 2.03 · 2.04) |
| 이바지하는 최상위 목표 | G-4 계측과 감사 추적 |
| 부트스트랩 순서 | git init → backlog.md CLI → `backlog init` → **coding-agent-git-commit-tool** → claude-code-agile-hooks (최상위 3.02) |
| 소비자 | agent-orchestrator의 `CommitLedger`가 Done 시점에 태스크 브랜치의 트레일러를 읽어 태스크 카드에 기록한다 (최상위 ORC-021) |

최상위 설계는 "커밋 = 함수, 커밋당 토큰 계량"을 핵심 성질로 둔다(최상위 1.02 P7). 그 성질을 실제
커밋 안에 남기는 것이 이 컴포넌트다. 역할마다 별도 프로세스로 뜨는 구조(최상위 1.02 P2)는 세션
트랜스크립트가 역할마다 따로 생긴다는 뜻이고, 이 컴포넌트는 그 트랜스크립트로 커밋마다 토큰을
잰다. 역할 세션별 귀속이 정확한지는 아직 실측 근거가 없다(최상위 TRL-007, `TBD(최상위 Q-18)`).
