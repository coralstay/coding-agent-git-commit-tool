# 0. 문서 정보

이 문서는 coding-agent-git-commit-tool의 설계 문서다. 상위 문서는 최상위 Sigkill Foundry 설계 문서이고,
이 컴포넌트는 그 3.03 컴포넌트 명세 §3에 해당한다. 스펙 주도 개발(SDD)을 따른다 — 구현은 이 명세에서
도출하고, 명세와 코드가 어긋나면 명세를 먼저 고친 뒤 코드를 맞춘다.

## 문서 구성

설계 문서는 다섯 문서로 이어진다. 문서마다 하나의 질문에 답하고, 앞 문서의 답이 뒤 문서의 입력이 된다.

| 번호 | 문서 | 답하는 질문 |
| --- | --- | --- |
| 1 | 프로젝트 제안서 | 왜 만들고, 무엇을 어디까지 하는가 |
| 2 | 요구사항 명세서 | 무엇을 만족해야 하는가 |
| 3 | 아키텍처 설계서 | 어떻게 구성되고 동작하는가 |
| 4 | 구현 계획서 | 어떤 순서로 만들고, 무엇으로 판정하는가 |
| 5 | 구현 결과 보고서 | 무엇을 만들었고, 판정은 어떻게 나왔는가 |

장은 `문서 번호.장 번호`로 가리킨다 (예: 3.05 설계 결정). 장 안의 절은 `§`로 가리킨다 (예: 3.03 §1).
최상위 Sigkill Foundry 문서의 장은 앞에 "최상위"를 붙여 가리킨다 (예: 최상위 3.03 §3).

## 규범 용어

| 표현 | 뜻 |
| --- | --- |
| 반드시 ~한다 (MUST) | 어기면 명세 위반이다 |
| ~해야 한다 (SHOULD) | 어길 때는 이유를 3.05 설계 결정에 남긴다 |
| ~할 수 있다 (MAY) | 선택 사항이다 |

## 요구사항 표기

- 목표는 `G-<번호>`로 식별하고 1.03 목표와 범위에 둔다. 최상위 목표는 "최상위 G-n"으로 적는다.
- 원칙은 `P<번호>`로 식별하고 1.02 원칙에 둔다. 최상위 원칙은 "최상위 P<번호>"로 적는다.
- 기능 요구사항의 영역 접두어는 `TRL`이다. 최상위 2.03이 이 컴포넌트에 쓰는 접두어와 같다. 품질 요구사항은 `NFR`이다.
- 요구사항 ID는 `<영역>-<세 자리 번호>`이고 번호는 재사용하지 않는다. 번호 공간은 최상위 문서 하나다.
  - 최상위 2.03의 `TRL-nnn`과 2.04의 `NFR-nnn`(이 컴포넌트는 NFR-004 · NFR-005)을 같은 ID · 같은 뜻으로 이어받는다.
  - 하위 번호나 이 저장소 전용 번호 대역(`TRL-101` 같은)은 두지 않는다. 최상위에 없는 요구사항이 필요하면 최상위 2.03 · 2.04에 먼저 올려 번호를 받는다.

- 설계 결정은 `ADR-<번호>`로 3.05에, 미결 사항은 `Q-<번호>`로 4.03에 둔다. 둘 다 이 저장소 안의 번호이고,
  최상위 것은 "최상위 ADR-n" · "최상위 Q-n"으로 적는다.
- 원천인 backlog decision은 `decision-<번호>`, 태스크는 `GF-<번호>`로 그대로 적는다.
- 모든 요구사항은 수용 기준을 하나 이상 가진다(4.02).
- 아직 정하지 않은 값은 `TBD(Q-n)`으로 적고, `Q-n`을 4.03 미결 사항에 둔다.

## 추적 규칙

모든 요구사항은 다음 사슬로 앞뒤가 이어진다. 사슬이 끊긴 항목은 둘 수 없다.

1. 최상위 요구사항 `TRL-0nn` · `NFR-0nn` (최상위 2.03 · 2.04) — 사슬의 위쪽 끝이다.
2. → 이 저장소의 목표 `G-n` (1.03) — 목표는 자신이 이바지하는 최상위 G-n을 적는다.
3. → 요구사항 `TRL-nnn` · `NFR-nnn` (2.03 · 2.04) — 최상위 ID를 그대로 받거나, `1nn`번대로 세분하며 상위 ID를 적는다.
4. → 구성 요소 · 인터페이스 (3.01 · 3.03 · 3.04) — 구성 요소는 자신이 구현하는 요구사항 ID를 적는다.
5. → 수용 기준 (4.02) · backlog 태스크 (4.01) — 요구사항 하나는 backlog 태스크의 AC로 내려간다. 태스크 카드는 자신이 구현하는 요구사항 ID를 적는다.
6. → 결과 판정 (5.02) — 수용 기준마다 통과/실패와 그 증거(테스트 로그 · 실측 커밋)를 남긴다.

- 최상위 요구사항의 문장이 바뀌면 이 저장소의 2.03 · 2.04를 먼저 맞춘다. 이 저장소가 최상위 요구사항을 바꿀 필요를 찾으면 최상위 문서에 먼저 올린다.
- 원칙(1.02)에 어긋나는 요구사항은 둘 수 없다. 원칙을 바꾸려면 3.05 설계 결정에 결정을 먼저 남긴다.
- 계획과 다르게 구현한 것은 5.03 계획 대비 편차에 적고, 해당 설계 결정(3.05)에 연결한다.

## 편집 규칙

- 설계 내용의 원본은 이 설계 문서 하나다. 편집 원본은 Claude 앱의 문서이고, 저장소의 `design/**/*.md`는 Claude가 동기화하는 사본이다. 둘이 어긋나면 Claude 앱 문서가 맞다. 새 근거가 생기면 Claude 앱 문서를 먼저 고치고 사본을 맞춘다.
- `backlog/docs` · `backlog/decisions` · README는 이 설계 문서의 원천이다. 설계 문서가 원천을 대신하지 않고, 원천을 지우지 않는다.
- 한 장 = 한 문서. 같은 내용을 두 장에서 고치고 있다면 한쪽을 장 참조 한 줄로 접는다.
- 외부 문헌은 저장소에 옮겨 담지 않는다(decision-14). 인용과 검증 상태는 부록 참고 문헌에서만 관리한다.
- 다이어그램 원본은 `design/diagrams/*.dot`이다. DOT으로 먼저 쓰고, DOT으로 표현할 수 없는 것(시퀀스 등)만 mermaid(`.mmd`)로 쓴다.
- `design/build-diagrams.py`가 원본을 `design/diagrams/<이름>.svg`로 렌더한다. 색은 원본에 센티넬 hex로 적고, 빌드가 SVG 안의 CSS 변수(라이트 기본 · 다크 재정의)로 바꾼다. 빌드 전제: graphviz(`dot`), mermaid 렌더용 `npx` + 로컬 Chrome.
- 생성된 SVG는 손으로 고치지 않는다. 원본을 고치고 빌드를 다시 돌려 같은 커밋에 넣는다. 장 사본은 `![설명](../diagrams/<이름>.svg)`로 참조한다.
- 저장소 Markdown의 외부 링크는 문서 맨 아래 링크 정의 블록에 모으고, 본문은 `[표시][키]`로만 쓴다.
