# 재설계 작업 순서와 의존성

DRAFT-19~29(promote 후 태스크)의 실행 순서와 그 근거. 계획 전문은 doc-13, 용어는 doc-14.

## 의존성의 근거는 파일 충돌이다

의존성을 "논리적으로 먼저인 것 같다"로 정하지 않고, **같은 파일을 건드리는지**로
기계적으로 확인했다. 결과:

| 겹치는 조합 | 공유 파일 |
| --- | --- |
| 19 · 20 · 21 · 22 · 23 · 24 · 27 | `hooks/prepare-commit-msg` |
| 22 · 26(구 범위) | `hooks/gitformat.conf` |
| 27 · 29 | `hooks/README.md` |

`hooks/prepare-commit-msg` 하나를 일곱 태스크가 단계적으로 채우므로 **19~24와 27은 직렬**이다.
병행 가능한 것은 25(`hooks/applypatch-msg` 단독)뿐이다.

## 순서를 정하며 고친 문제 두 가지

의존성을 검토하다 초기 분할의 결함 두 개를 발견해 태스크 범위를 조정했다.

### 1. 이중 실행 구간 — 구 훅 삭제를 기능 이전과 같은 커밋으로 합쳤다

처음에는 구 훅 3개 삭제를 마지막 정리 태스크에 모아뒀다. 그러면 기능을 옮긴 뒤 삭제까지의
구간에서 **lint·검증·트레일러 삽입이 두 번** 일어난다. 특히 트레일러 이전 시점이 위험하다 —
`prepare-commit-msg`가 넣은 트레일러에 `post-commit`이 `Signed-off-by`와 `Verify-Bypassed`를
또 붙인다. **이 저장소는 자기 훅으로 커밋하므로 그 잘못된 footer가 실제 이력에 남는다.**

그래서 각 기능을 옮기는 태스크가 그 기능의 구 훅을 같은 커밋에서 삭제한다.

| 태스크 | 옮기는 기능 | 같은 커밋에서 삭제 |
| --- | --- | --- |
| 20 | lint | `hooks/pre-commit` |
| 21 | 메시지 검증 | `hooks/commit-msg` |
| 22 | 트레일러 삽입 | `hooks/post-commit` |

정리 태스크(26)에는 `install.sh`의 `commit.template` 제거와 `.gitmessage` 삭제만 남는다.

### 2. 안전망 없는 훅 변경 — 테스트 프레임워크 전환을 맨 앞으로 옮겼다

처음에는 테스트 이관을 마지막에 뒀다. 그러면 훅을 바꾸는 동안 bats를 계속 고쳐야 하고,
마지막에 그걸 전부 Python으로 다시 쓰게 되어 **두 번 일한다.** 게다가 구 훅을 검증하는
bats 파일이 훅과 함께 사라지므로 중간 구간에 안전망이 얇아진다.

그래서 이관을 **맨 앞**에 두고, 범위를 **동작 무변경 1:1 이관**으로 좁혔다. 구 훅 3개를 그대로
검증한 뒤, 그 Python 스위트를 안전망으로 삼아 훅을 바꾼다. 새 동작(에디터 거부, 귀속 측정
등)의 테스트는 각 동작을 구현하는 태스크에서 함께 작성한다.

이관 태스크가 기존 테스트를 **깨뜨리지 않았는지** 확인할 방법: 이관 전 `bats tests/`와 이관 후
`python3 -m unittest discover -s tests`의 케이스 수와 통과 여부를 비교한다. 훅 코드는 이
태스크에서 한 줄도 바꾸지 않으므로 동작이 같아야 한다.

## 작업 순서

```
[0] 테스트 프레임워크 이관 (동작 무변경)          ← 안전망 먼저
     │
[1] prepare-commit-msg 골격 (면제 + -m 게이트)
     │
[2] lint 이전        + pre-commit 삭제
     │
[3] 메시지 검증 이전  + commit-msg 삭제
     │
[4] 트레일러 삽입 이전 + post-commit 삭제 + conf 트레일러 키 정리
     │
[5] 토큰·툴콜 측정 재작성
     │
[6] 에이전트 판정 재작성
     │
[7] applypatch-msg 신설 (git am 차단)             ← 파일이 달라 [1]~[6]과 병행 가능
     │
[8] 설정 정리 (install.sh commit.template, .gitmessage)
     │
[9] 파일·디렉터리 개칭 (checks→lint, conf→defaults 등)
     │
[10] README·hooks/README.md 재작성                 ← 최종 상태를 문서화
```

| 단계 | 태스크 | 의존 | 근거 |
| --- | --- | --- | --- |
| 0 | 테스트 이관 | 없음 | 안전망을 먼저 세운다 |
| 1 | prepare-commit-msg 골격 | 0 | 이후 모든 훅 변경의 토대 |
| 2 | lint 이전 | 1 | 같은 파일 |
| 3 | 메시지 검증 이전 | 2 | 같은 파일 |
| 4 | 트레일러 삽입 이전 | 3 | 같은 파일 + conf |
| 5 | 토큰 측정 | 4 | 트레일러 삽입 경로가 있어야 값을 넣을 수 있다 |
| 6 | 에이전트 판정 | 5 | 토큰 측정이 판정 결과를 참조한다 |
| 7 | applypatch-msg | 1 | 코드 관례(인코딩 고정 등)를 1에서 정한 뒤 따른다. 파일이 달라 병행 가능 |
| 8 | 설정 정리 | 4 | 에디터 거부가 동작한 뒤 `commit.template`을 지운다 |
| 9 | 개칭 | 8 | 지울 파일을 먼저 지우고 남은 것만 개칭한다 |
| 10 | 문서 재작성 | 9 | 최종 파일명이 확정된 뒤 |

## 왜 개칭(9)을 늦게 두는가

개칭을 먼저 하면 이후 모든 태스크의 diff에 이름 변경과 내용 변경이 섞여 리뷰가 어려워진다.
또 8에서 삭제할 파일을 미리 개칭하면 지울 것을 옮기는 헛일이 된다. 삭제를 끝내고 남은
파일만 개칭하면 diff가 순수 rename이 되어 `git mv`로 이력에서 추적된다.

## 각 단계의 커밋 단위

decision-22에 따라 커밋 하나는 논리적 변경 하나(함수 하나 수준)다. 한 태스크가 여러 커밋이
되는 것이 정상이며, 각 커밋은 AC 하나를 만족시키는 크기를 지향한다. 태스크 경계와 커밋 경계는
다르다.
